# Scenario Design Checklist

Run through this checklist after drafting a scenario. Every unchecked item is a potential problem to address before delivering.

For Brigade Fire and Fury 2nd Edition, first apply [the mandatory system reference](references/brigade-fire-and-fury.md). Its map prerequisite overrides the geometry, spacing and text-only setup checks below: with a completed map, verify those checks against it; with a pending map, mark them deferred and require sourced relative descriptions plus a separate map-agent handoff. Do not claim setup readiness or validated contact timing for a pending map. Other systems retain the generic checks.

## Brigade Fire and Fury 2nd Edition presentation

Apply only to that system:

- [ ] All commands use the required commander line, six-column OOB, single-paragraph Effectiveness header and native bulleted notes.
- [ ] Combat Strength and numeric Heavy Casualties summaries match the OOB; miniatures gun counts do not add limbers.
- [ ] The full rules name, reinforcing group terminology, feet for the table, and inches for valid mapped distances are used.
- [ ] Every table-edge location or entry measurement identifies its edge, starting reference and direction; no raw x/y grid or stale pending-map geometry remains.
- [ ] VP conditions are individual native bullets; approved casualty/control templates have scenario-specific variables and bold lead-ins intact.
- [ ] Redundant core-rule explanations and Project References are absent; historical Sources and real scenario exceptions remain.
- [ ] Playing time ends with the required not-including-setup wording; when the scenario is unplaytested, its status is in an actual repeating footer, verified on every rendered page.

## Objectives & Victory

- [ ] Victory conditions are objective-based (not pure elimination)
- [ ] Objectives create meaningful choices. A single extended or compact objective has viable tactical options.
- [ ] Both sides can realistically win
- [ ] Victory conditions can be explained in 2 sentences or less
- [ ] A turn limit or game-end trigger exists
- [ ] For historical scenarios: the historically losing side has a viable path to victory
- [ ] Scoring and control are clear before play. Legitimate hidden missions have separate handling.
- [ ] Exit requirements account for arrivals, travel, opposition, and possible premature completion, if applicable.
- [ ] Casualty constraints define counted losses and do not reward inactivity over the mission, if applicable.

## Forces & Balance

- [ ] Forces are asymmetric in composition, objectives, or information
- [ ] Attacker has appropriate numerical or qualitative advantage (typically 1.5:1 to 3:1)
- [ ] OOB is organized hierarchically matching the game scale
- [ ] Quality/experience ratings are assigned to all units
- [ ] All equipment is named at the correct specificity for the scale (consult oob-equipment-conventions.md):
  - Skirmish: individual weapons named per model (e.g., "Kar98k", "M1 Garand")
  - Platoon: weapons named per squad (e.g., "Bren Mk I", "MG 42 team")
  - Company+: FOW-style team types used (e.g., "Rifle/MG team", "6-pdr Anti-Tank Gun")
  - Vehicles always named by specific variant (e.g., "Panzer IV H", not "Panzer IV")
- [ ] Forces match what the user said they have available (if specified)
- [ ] Variable forces or fog-of-war elements add replay value (where appropriate)

## Terrain

- [ ] Terrain density is appropriate for the period and scale (consult rules-of-thumb table in scenario-design-patterns.md)
- [ ] Terrain creates meaningful choices (cover vs. speed, LOS vs. concealment)
- [ ] Several viable approaches exist, or a mission-defined chokepoint offers feasible timing, support, reserve, or objective choices.
- [ ] Which table edge is North is declared before any directional references
- [ ] Every terrain feature has: position in inches from table edges, dimensions in inches (e.g., 8" x 6"), and explicit gameplay attributes (Tall/Short, cover type, LOS effects)
- [ ] Terrain is historically/geographically appropriate for the battle's region
- [ ] Deployment zones are specified with precise measurements from table edges, dimensions, and any restrictions
- [ ] River crossings and other bottlenecks have feasible capacity, protection, and timing for the intended task.
- [ ] Dominant firing positions leave the opponent feasible choices.
- [ ] Physical terrain simplifications preserve native observation, movement, cover, and objective effects. Wooded elevation is checked explicitly.

## Gameplay

- [ ] Opening activity suits the mission. Short combat-focused games target contact within turns 1-2. Other pacing has a stated purpose.
- [ ] No more than 3 scenario-specific special rules
- [ ] Each special rule creates a meaningful player decision
- [ ] There is a reason to maneuver rather than sit and shoot
- [ ] Both sides have meaningful decisions, including defender movement or commitment choices where the mission permits.
- [ ] Reinforcement timing creates uncertainty or decision pressure (if reinforcements exist)
- [ ] Unfamiliar core subsystems and special rules fit player experience and available time.
- [ ] Session duration, simulated duration, and achievable actions are distinguished. Deadlines allow deployment, travel, and tasks.
- [ ] The session cutoff has a scoring procedure that preserves native mechanics where possible.
- [ ] Untested duration and balance are identified as estimates. Observed timings are recorded when available.

## Presentation

- [ ] Background narrative is vivid but under 4 paragraphs
- [ ] Player briefings are written from the player's perspective (2nd or 1st person)
- [ ] Terrain description is clear enough to set up without a visual map
- [ ] All scenario-specific stats and modifiers are provided (no rulebook lookup required for scenario elements)
- [ ] Estimated play time is realistic for the scenario scope and scale
- [ ] The estimate states its setup and briefing assumptions. System-specific wording takes precedence.
- [ ] Historical facts, estimates, and model substitutions are distinguished. Player knowledge is credible.

## Context-Specific

Check the items below that match your scenario type. These supplement the checks above.

- [ ] **Hidden deployment:** Native markers or private records identify positions. Any required maps match the table. Reveal, information handling, and adjudication are prepared and timed.
- [ ] **Multiplayer:** Each player has useful opening decisions. Nobody controls only late reserves without an initial role.
- [ ] **Multiplayer:** Activation reliability and command allocation are reviewed without altering native mechanics or historical ratings.
- [ ] **Multiplayer:** Parallel sectors preserve shared timing and cross-sector interactions, if used.
- [ ] **Multiplayer:** Communication limits have a scenario reason and a clear message procedure, if used.
- [ ] **Preparation:** Scenario data, reference sheets, maps, dice, measures, and counters are available where needed.

- [ ] **Convention:** Scenario runs with variable player counts (1 to max listed)
- [ ] **Convention:** Each player's briefing fits on one page
- [ ] **Solo/Coop:** AI activation system is fully specified
- [ ] **Solo/Coop:** Escalation mechanic increases tension over time
- [ ] **Campaign:** Consequences for the next scenario are noted
- [ ] **Historical:** The actual historical outcome is noted for comparison in designer's notes
